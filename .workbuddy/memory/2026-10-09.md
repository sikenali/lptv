## 分析：pytv 原理 & mygo 能否做 web 播放

**pytv 原理（三套实现同一条主线 = 寄生式取流）**
- 核心：不调/不伪造官方取流接口，加载官方 TV 页 + hook `Hls.prototype.loadSource` / `get_live_info`（XHR+fetch）捕获签名后 m3u8；换台 = 点击官方侧栏 `.tv-main-con-r-list-left > div[data-pid]`；`inject.js` 三套复用零修改。
- 三套差别只在"谁渲染、谁解密"：
  1. 原始 pytv：Windows pywebview + WebView2（Edge Chromium，自带 Widevine）→ 复用官方 video 解密。
  2. `pytv/native`：Linux 盒子 pywebview 强制 `PYWEBVIEW_GUI=qt` → QtWebEngine（Chromium ≥118）；需自备 `libwidevinecdm.so` + 容器 flags；必须盒子有本地显示（HDMI/X 会话），**非 web**。
  3. `lptv-web`（本仓库主实现）：**不需要 Widevine**。Playwright(headless chromium) 拿签名 playurl（60s 缓存 + 3 次重试）→ `hlsProxy.ts` 把 m3u8 内所有 URI（KEY/MAP/MEDIA/分片/嵌套）改写成同源 `/api/stream?u=<base64>&t=` 透传 → `player.js` 自建 video + hls.js(MSE) 播放；伪造侧栏让 inject 的 switchChannel 命中；`adapter.js` 把 `window.pywebview.api.*` 翻译成 fetch，inject.js 零修改。同源化是录/截（canvas 不污染）的前提。

**结论：egoist/mygo 不能用于此项目的"web 播放"**
- mygo = Go 桌面 App 框架（web 窗口用系统 webview：macOS WKWebView / **Linux WebKitGTK 4.1** / Windows WebView2；或 Go 自绘原生 UI），不是 web server、不是播放器。纯 Go 无 cgo，单文件二进制。
- 硬伤：Linux 后端 = WebKitGTK，**无 Widevine**（仅 ClearKey；EME 走 GStreamer+Thunder/OCDM，桌面发行版无 CDM）。全仓库 grep 无 widevine / EME / requestMediaKeySystemAccess；`internal/linux/window.go` settings 只设 DevTools/file access/clipboard/UA/zoom，未涉及 encrypted-media。→ 等于 pywebview 的 GTK 后端，播不了官方加密流。
- macOS WKWebView 只有 FairPlay；Windows WebView2 有 Widevine（可播）但 mygo 未暴露 WebView2 `AdditionalBrowserArguments`，无法传 `--autoplay-policy=no-user-gesture-required` / `--widevine-path`（已 grep 确认 internal/windows 无此参数）。
- mygo 具备：UA 覆盖（Page.SetUserAgent / WindowOptions.UserAgent）、userScript 注入（可做"打开官方页 + 叠 UI"）、LoadURL 远程页、custom protocol（`mygo.Protocol.Handle` 可做 Go 版同源反代）。
- 若只想给"同源代理 + hls.js"这条 web 路线做个桌面壳，mygo 可行（Go 侧实现 proxy/typed IPC），但那不是"web 播放"能力，浏览器本身就能播；要"盒子通过 web 给任意设备播放"应继续走 lptv-web + 懒猫 LPK web 模式（routes/upstreams）。
- 另注：mygo 要求 Go 1.27+ / Bun，仓库很新（成熟度有限）。

## 追加：pytv/native（PYWEBVIEW_GUI=qt）可行性核查

**结论：路线成立，但当前这套文件按原样跑不出画面。**

已验证事实：
1. `--widevine-path` 是 QtWebEngine 官方支持的开关（Qt 文档：QtWebEngine 支持 Widevine CDM，需自备，可用 QTWEBENGINE_CHROMIUM_FLAGS 的 widevine-path 指定路径）。pywebview 的 `qt` 后端确实用 QtWebEngine（`webview/platforms/qt.py` 导入 `qtpy.QtWebEngineWidgets`，renderer='qtwebengine'；`guilib.GUIType` 含 'qt'）。→ 骨架成立。
2. **官方 linter 实测**（`lzc-cli/lib/app/manifest_lint.js` 的 `collectManifestLintWarnings` 跑 `pytv/native/lzc-manifest.yml`）：
   `[warn] unknown-manifest-fields: application.backend_launch_command, application.volumes` → **这两个字段不生效**（正确位置：`backend_launch_command` 属于 `application.upstreams[]` 条目；卷是 `services.<name>.binds`）。对照 `lzc/lzc-manifest.yml` 只报 locales 警告 → web 版清单是干净的。
3. lzc-manifest 合法字段（application）：image/background_task/subdomain/secondary_domains/multi_instance/usb_accel/gpu_accel/kvm_accel/file_handler/entries/routes/upstreams/injects/public_path/workdir/ingress/environment/health_check/oidc_redirect_path/handlers/user_app/depends_on（depends_on 已弃用）。services.<name>：image/environment/entrypoint/command/tmpfs/depends_on/healthcheck/health_check/user/cpu_shares/cpus/mem_limit/shm_size/network_mode/netadmin/setup_script/**binds**/runtime。
4. **平台有官方 GUI 通道**：lzc-cli 自带 `template/gui-vnc/` —— 基镜像 `registry.lazycat.cloud/kasm-debian-bookworm:0.0.1`（KasmVNC 桌面），manifest 用 `routes: /=http://desktop:6901/` + `services.desktop.{image: embed:app-runtime, user: lazycat:kasm-user}`，GUI 由 `~/.config/autostart/startup-script.sh` 在虚拟桌面里拉起。→ GUI 应用不必依赖盒子本地 X 会话，浏览器访问即可。
5. lzc-build.yml 的 `images.<alias>` 支持 `builder: remote|local`、`context`/`dockerfile`/`upstream-match`；manifest 用 `image: embed:<alias>` 引用。当前用手写 `docker build` + `image: localhost/lptv-native:1.1` 不是规范路径（linter 报 store-image-registry-invalid）。

**三个必须改的点**
- 显示：`DISPLAY=:0` 依赖盒子本地 X，改走 gui-vnc（Xvfb/KasmVNC :6901 + routes）。
- CDM 接线：manifest 的 QTWEBENGINE_CHROMIUM_FLAGS 缺 `--widevine-path`；start.sh 是唯一做该展开的地方却被绕过；main.py 完全不读 WIDEVINE。应在 main.py 里 `import webview` 之前拼好 QTWEBENGINE_CHROMIUM_FLAGS（含 --widevine-path + --no-sandbox）。
- CDM/内核版本必须配对：CDM 与 Chromium ABI 严格耦合（社区数据：CDM 4.10.2209.0 ⇔ Chromium 116+；2026 年 CDM 已 4.10.29xx）。Qt 6.7=Chromium 118 已过旧，应用当前 PyQt6-WebEngine 并配相近版本 CDM。另注意 `--no-sandbox` 是前提（非默认路径的 CDM 无沙箱加载不了，QTBUG-78709）。

## 追加：提交（commit 00a8da6）时发现并修掉的 CRLF 隐患

**提交**：`00a8da6 refactor: 仓库收敛为 KasmVNC 单线，去重并移除 Web 版 v1`（42 files, +1305 −5047）。
`.workbuddy/` 已加入 .gitignore（代理本地状态，不入库）。

**隐患（重要，容易踩）**：本机全局 `core.autocrlf=true`，而仓库**没有 .gitattributes**。
后果：`git add` 时警告 "LF will be replaced by CRLF"，clone 到 Windows 后
`lzc/build.sh` / `lzc/images/startup-script.sh` / `Dockerfile` 会变成 **CRLF** →
容器里 `/bin/sh` 直接执行失败（`^M` 报错），且 Dockerfile 的 `RUN \` 续行也可能被破坏。

**修法**：新增 `.gitattributes` 强制 `* text=auto eol=lf` + `*.png binary` 等二进制白名单，
再清掉存量 8 个文件的 CR。**验证要字节级**（`tr -cd '\r' < f | wc -c` 应为 0），
因为 `git ls-files --eol` 受 stat 缓存影响会误报，`grep -q $'\r'` 在本环境也不可靠。

**踩坑**：`git checkout-index -f -a` 与 `git add --renormalize .` 都**没能**把工作区文件转成 LF
（索引变了、磁盘没变），最后靠 `sed -i 's/\r$//'` 逐个清干净。

**校验死角**：`lzc/icon.png` 有 435 个 CR 字节，那是 PNG 二进制数据，**不是**换行问题
（`git ls-files --eol` 标记 `i/-text`）；写校验脚本时要跳过二进制。

## 打包 + 安装（LPK 已落地）

**产物**：`lzc/cloud.lazycat.app.lptv-v1.1.0.lpk`（177 MB / 169 MiB），**已安装**成功，
应用地址 `https://lptv.jinglebaby.heiyu.space`（返回 307 → 微服登录页，说明路由已注册）。

**打包链路上的三个真实坑（都改了代码）**：
1. **`buildscript: ./build.sh` 在 Windows 必挂** —— lzc-cli 按平台选 shell（Linux `sh -c` / Windows `cmd /c`），
   `.sh` 在 cmd 里直接语法报错。→ 换成 `build.cjs`（node 两平台都在 PATH）。
2. **镜像构建上下文漏收 `app/`** —— lzc-cli 用 `fast-glob(path.join(from,'**'))` 收集 COPY 目录源，
   Windows 上 `path.join('app','**')` 产出反斜杠 `app\**` → glob 返回空 → `app/` 没进上下文，
   构建报 `copier: stat "/app": no such file or directory`。→ Dockerfile 改「逐文件 COPY + 多源同目标」，
   并在 `build.cjs` 里加 **Dockerfile COPY 覆盖率校验**（漏拷直接 fail）。
3. **本机 Node 的 `spawnSync` + stdin pipe 必 EBUSY**（v22/v24 都复现，bash/cmd 下都一样；
   stdin=ignore/异步 spawn 正常）—— lzc-cli 经 `cross-spawn.sync` 调 ssh 正是 stdio:['pipe','pipe','pipe']，
   打包会卡在「检测懒猫开发者工具」。→ `lzc/scripts/spawnsync-stdin-fix.cjs` 预载补丁，
   仅在首次 EBUSY 时把 stdin 换成 ignore/临时文件重试；正常机器上是 no-op。`package.sh` 已自动注入。

**环境坑**：本机 lazycat 客户端（shellapi 127.0.0.1:28325）**时连时断**；不在线时
`lzc-cli project info/log`、`box list` 全会报「获取盒子信息失败」，直连 `ssh box@<domain>` 也会返回空。
所以**归档时无法查容器日志**，运行态端到端验证只能等客户端在线后在 VNC 桌面里实测。
